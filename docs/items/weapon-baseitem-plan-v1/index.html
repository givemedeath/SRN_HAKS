The decisions we are planning around

  • Custom Shadowrun combat. Per-item gameplay profiles own damage, AP, skills, reach and firing modes.
  • Preserve handling. One-handed, two-handed, melee, ranged and throwing behaviors remain distinct.
  • Script firearm ammunition. Magazines, reloads and ammunition selection do not require player-managed native gun ammunition slots.
  • Dual-wield suitable firearms. Eligibility belongs to each weapon/state; it is not granted to every SMG.
  • Custom inventory UI. Standard native footprints within each family; per-item UI art and storage rules stay in item data.
  • Shadowrun-only content. Existing stock types can be repurposed after compatibility checks.
  • Implants and mounts use their systems. No ordinary hand-held weapon type for every cyberweapon or vehicle gun.
  • Reuse without conflating gameplay. Flechettes are base-weapon ammunition modes. Four launcher records stay separate and use their parent models.

The exceptions have explicit routes

Keep a tooling limit from multiplying base types

Recommended addressing change: Allocate a raw model-part appearance ID for each actual design/finish. Keep all values within the current 0–255 byte contract initially. Do not reserve nine finish positions for every design or tie the bottom/middle/top slot permanently to pistol/SMG/rifle categories.
  1. Preserve approved appearance numbers, textures and invisible placeholders exactly.
  2. Prove that two different complete models at adjacent raw appearance IDs remain distinct after save/reload and multiplayer replication. Test both shipped Human bodies and multipart icons.
  3. Keep one exact allowed assembly per blueprint. A shared base type does not allow arbitrary mixing of models.
  4. If flat addressing fails its controlled test, document the smallest required overflow bank and its added numeric-row count. It is a capacity exception, not an eleventh handling family; do not change the layout silently.

This is a proposed allocator extension. The current code has not been changed, and no larger engine limit is assumed. Existing model addresses are reserved before any new allocation.

Implementation in four bounded passes

1 · Freeze the ten-family planning baseline and protect approved assetsKeep all 283 stable item IDs, the three flechette source merges, parent-model links and eight holds. Treat the candidate numeric rows as a test configuration. Keep the four approved weapon packages byte-for-byte, including short-sword row 0 until a separately validated migration is appropriate.
2 · Validate the ten carriers and shared presentationsDemonstrate the shared one-handed melee presentation, the combined longarm/crossbow presentation and knife hand/equipment behavior. Check single- and dual-firearm attacks without player native gun-ammo slots, exactly one authoritative ammo mutation, correct off-hand ownership, two-hand restrictions and the required bows/throwing/shield motions. Test both shipped Human bodies, special poses, wearable coexistence and raw appearance IDs. Record any necessary exception and its count effect; do not silently change the baseline.
3 · Adopt the proven rows and build through itemkitAfter focused checks pass, set the numeric rows/fields and reserve resources against the full namespace. Convert selected source models into exact carrier assemblies; do not regenerate geometry merely for a base-type change. Blade/blunt damage and crossbow/firearm ammunition remain profile data. Regenerate or adapt only the affected icons/exports for the shared native footprints. Use focused affected tests, not a full regression run.
4 · Review an additive private packageInclude both shipped Human bodies, examples covering all ten carriers, shared-family edge cases and the unchanged approved weapons. Keep user-controlled client acceptance separate from the design and native checks. This planning review does not launch a client or promote production.

The current SR_NWN combat slice excludes dual-wielding; that remains an explicit gameplay extension. A custom inventory UI does not itself prove native hand, attachment or animation behavior.
